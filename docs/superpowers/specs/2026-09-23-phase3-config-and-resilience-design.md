## 5. 配置机制（#1 / #2 共用）

**载体**：`pc-kvm.ini`，与 exe 同目录（`AppDomain.CurrentDomain.BaseDirectory`，与 jar、日志同处）。
INI 风格 `key=value`，键名纯 ASCII，`;` 起注释。

| 键 | 类型 | 默认 | 范围 | 生效时机 |
|---|---|---|---|---|
| `MouseSensitivity` | 小数 | `0.50` | `0.10`–`3.00` | 即时（每次按键事件读取当前值） |
| `PhoneSide` | `Left` / `Right` | `Right` | — | 保存即生效（重建 tracker） |
| `AllowKillAdb` | `true` / `false` | `false` | — | 即时（§9 第③级读它） |
| `ReconnectSeconds` | 整数 | `5` | `2`–`60` | 即时（监督线程每轮重读） |

**默认值即当前行为**：`Right` + `AllowKillAdb=false` 时行为与阶段二完全一致，
即"把 exe 单独拷到一台新机器上，跑起来和以前一模一样"。

**坏文件策略**：解析失败 / 键缺失 / 值越界 → **用默认值**，并在日志打**一行**说明哪一项回退了。
**绝不因为配置坏掉而拒绝启动或弹模态框**（本项目已有一次"模态 MessageBox 永久阻塞"的教训）。

**设置对话框**（`src/agent/SettingsForm.cs`）：托盘右键 →「设置…」
- 鼠标速度：`TrackBar`，0.10–3.00、步进 0.05，**实时显示当前数值**（速度必须边调边试手感，
  菜单项 `+`/`−` 做不到）
- 手机在：左 / 右 单选
- 「允许自动强杀 adb 进程」（附一行说明它会打断其它用 adb 的工具）
- 确定 = 应用 + 写回 ini；取消 = 丢弃

> 对话框本身会抢前台：若此刻处于接管态，250ms 守卫会按既有逻辑解除抑制——**这是期望行为**，

## 6. #1 鼠标移动速度

**现状**：`Program.cs:68` 已有 `double sensitivity = 1.0;`，并在 `:148-149` 用于
`(int)(e.Dx * sensitivity)`。所以本需求**不是**新造缩放模型，而是把已有的孤立字面量接到配置。

**语义**：系数乘在**转发给手机的增量**上；虚拟光标模型用**缩放后**的增量推进
（`cursor.NextDx(scaled)`），因此"模型记账"与"手机真实位移"始终自洽。
**不受影响**的两处：回程阈值 `BackPushThreshold=40`（单位是**原始** mickey，≈1cm）、
入屏比例映射（由 PC 光标绝对位置算，与增量无关）。

**必须做的实现细节 —— 小数余量累积**：
现在的 `(int)(e.Dx * sensitivity)` 在系数 < 1 时会把小位移**截断成 0**
（`dx=1`、系数 0.5 → 0 像素）。表现为**慢速移动发涩、细调走不动**——恰好是低灵敏度下
最常用的场景。故每轴维护一个 `double` 残差：
```
res += dx * sensitivity;
int send = (int)Math.Truncate(res);   // 向零截断，与发送语义一致
res -= send;
```
`Reset()` / `SetPosition()` 时残差一并清零（避免跨越入屏后带着上一次的零头）。

**不做**（YAGNI）：X/Y 各自系数、加速度曲线、按应用区分的灵敏度。

## 7. #2 手机在哪侧（只做左/右）

**配置**：`PhoneSide = Left | Right`（§5）。

**入口边改为运行时推导**，废掉 `Program.cs:73` 的 `3839 / 0 / 1080` 魔数：
- `Right` → `edgeX = SM_CXVIRTUALSCREEN - 1`（Windows 把光标钳在最后一列，故取 `W-1`）
- `Left`  → `edgeX = 0`
- `edgeTop = 0`，`edgeBottom = SM_CYVIRTUALSCREEN`

沿 Ruling 21 的约定：**`_edgeX` = 触发侧最外侧"有效像素列"的 x**（右侧 3839、左侧 0）。
不这样做的话，换显示器布局会让入口条件**永远不可达**——正是 Task 6 审查栽过的静默 bug。

**切换时机**：设置保存时若 `tracker.Current == Takeover`，先 `AbortTakeover()`（含 `supp.Release()`
与补发 LEAVE），再按新边重建 tracker。Idle 态无状态可丢，直接重建。

**⚠️ A3 耦合（必须真机验收，代码层面解不了）**：手机在左侧时，若**旋转**让"物理上邻接 PC
的那条边"映射到另一条逻辑边，回程几何就错——用户会遇到"设了左侧、旋转后回不来"。这是阶段二
挂账的 A3。故 #7 落地后必须**横屏、竖屏各测一次**，两个方向都测。

**补齐左挂回归**：harness 现 15 条全是 `phoneRight: true`。新增镜像用例覆盖
入口判定、竖直安全带、比例入屏（`phoneX` 取 `_phoneW-1`）、回程边与累积、冷却再武装。

## 8. #5 数字键盘与 NumLock

### 8.1 实测根因（2026-09-23，本机真机日志，铁证）

让用户把 PC NumLock 关掉后按键，`pc-kvm.log` 逐行记录：

```
KEY scancode=0x45   DOWN/UP   ← NumLock 键本身
KEY scancode=0x47   DOWN/UP   ← 小键盘 7：普通 0x47，【没有 E0 前缀】
KEY scancode=0xE047 DOWN/UP   ← 导航区那颗独立 Home：才是 E0 0x47
```

**结论**：物理数字键盘**不受 NumLock 影响，恒发同一个普通 scancode**；是 Windows 依据
NumLock 把它解释成 `NUMPAD7` 还是 `HOME`。E0 前缀属于**导航键区的独立键**。

因此 `ScancodeMap` 里那句注释 —— "NumLock 关时同样这些物理键发 E0 前缀，走上面 E0 表的
Home/End/箭头那一组" —— **是错的**。而 `0x47 → 0x5F (KP7)` 因此**无条件**生效：
**PC 的 NumLock 关着，手机照样收到小键盘 7** → 这就是用户报的"灯与实际相反"。

> 为什么阶段二没发现：两次真机实测（`0x52 0x52 0x47 …` = 小键盘 `0 0 7 …`；`0x50 0x52 0x50 0x4D`
> = `"2026"`）**都是 NumLock 开着打数字**，关的那一侧从未被测过。`FINDINGS.md:63` 当年也已
> 明写"scancode 的 E0 处理分支**未被实测覆盖**"。

### 8.2 修法：PC 侧按 NumLock 翻译（不设备侧改）

NumLock 状态**住在 PC 上**，所以翻译也在 PC 上做，线上协议不变：

1. 读 `GetKeyState(VK_NUMLOCK) & 1`（UI 线程调用，纳秒级开销）
2. 若 NumLock **关**，把数字键盘的普通码翻成**导航等价码**（下表）
3. NumLock **开** → 原样送（走既有的 `0x47 → 0x5F` 那段）

| 小键盘码 | NumLock 开 | NumLock 关 |
|---|---|---|
| `0x47` 7 / `0x48` 8 / `0x49` 9 | `0x5F` / `0x60` / `0x61` | `0x4A` Home / `0x52` ↑ / `0x4B` PgUp |
| `0x4B` 4 / `0x4C` 5 / `0x4D` 6 | `0x5C` / `0x5D` / `0x5E` | `0x50` ← / （Clear，HID 无对应，丢弃） / `0x4F` → |
| `0x4F` 1 / `0x50` 2 / `0x51` 3 | `0x59` / `0x5A` / `0x5B` | `0x4D` End / `0x51` ↓ / `0x4E` PgDn |
| `0x52` 0 / `0x53` . | `0x62` / `0x63` | `0x49` Insert / `0x4C` Delete |
| `0x37` `*` / `0x4A` `-` / `0x4E` `+` / `0x35` `/` | 原值 | **原值**（不受 NumLock 影响） |

注意"NumLock 关"这一列的 usage **与 `ScancodeMap` 既有 E0 表逐项相同** —— 因为导航区
独立键与"NumLock 关时的小键盘"本来就是同一批语义。故设备侧**一行都不用改**，只需修正注释。

**NumLock 键本身继续转发**给设备（usage `0x53`）。理由：这样 Android 自身的 numlock 状态
跟随 PC 一并翻转。若某些 Android 版本会按**自己**的 LED 状态翻译小键盘码，这条转发让两种
假设都成立；实测本机 Android 未发生该翻译（功能正常），故属防御性一致。

**实现位置**：新纯函数放进 `KeyMap.cs`（如 `NumpadNavFor(mk)` + `Translate(scancode, isE0, numLockOn)`），
便于离线测。`Program.cs` 只多一行取 NumLock 状态并调用翻译——**日志照旧打原始 scancode**
（日志必须记录真实观测，不能记录翻译后的值）。

### 8.3 顺带查证（结论：非缺陷，写下来免得重复怀疑）

同一批日志里还有一段看着可疑的序列：

```
KEY scancode=0xE02A DOWN / 0xE049 DOWN/UP / 0xE02A UP
```

`0xE02A` 是**假 Shift**（部分键盘给导航键区发的兼容前缀）。**已核实无害**：
`KeyMap.ModifierBit` 的 E0 分支只含 `0x5B/0x1D/0x38/0x5C`，**不含 `0x2A`** → 返回 0，
**不会往手机注入幽灵 Shift**；`0xE049 → 0x4B (PgUp)` 也正确。
**不改代码**，只把这条结论写进注释/测试，避免下一个人再查一遍。

## 9. #4 断联自愈

**监督线程**（放 `Watchers.cs`）：每 `ReconnectSeconds` 秒检查一次。未连接则**分级升级**：

| 级 | 动作 | 触发条件（"失败"一律定义为：**该周期结束时 `transport.IsConnected` 仍为 false**） |
|---|---|---|
| ① | 重建隧道 `adb reverse tcp:27183 tcp:27183` + 重启设备侧注入器 | 每次发现未连接 |
| ② | `adb kill-server` + `start-server`（温和，不碰别的进程） | **连续 3 个周期**结束时仍未连接 |
| ③ | `taskkill /F /IM adb.exe` + `start-server`（激进） | ②之后**再连续 3 个周期**仍未连接 **且** `AllowKillAdb == true` |

（`ReconnectSeconds` 默认 5s ⇒ 第②级约在 15s 后介入，第③级约在 30s 后。任一级成功连接即把
计数与档位归零。）

**为什么③要开关且默认关**：本机同时跑着 **3 个 adb**（两个 platform-tools + InputShare 自带的
一个），强杀会打断其它正在用 adb 的工具。真正管用的恢复手段是有破坏性的，所以把风险最大的
那一步交给用户显式开启。

**幂等**：每次重启注入器**前先 Kill 旧的**，否则设备侧会堆积多个 `app_process` 进程。

**jar 只推一次**：把 `DeviceLauncher.Prepare` 拆成 `EnsureTunnel` / `PushJar` 两步；
重连只走 `EnsureTunnel` + `Start`（jar 还在 `/data/local/tmp` 就不必每次重推）。

**可见性**：状态条显示 `等待设备…（已重试 n 次）`；日志**只在状态变化时**打一行
（不每次重试都打——本项目既有过"2% 采样率导致无法证伪"与"刷日志淹没有效信息"两种教训）。

**⚠️ 覆盖边界（必须如实写进文档与交接）**：2026-09-23 现场实测到一次掉线，
其性质是**设备级**的——`adb devices` 全空、Windows 侧 `Android ADB Interface`
（`VID_18D1&PID_4E11\04053891899C1540`）状态 OK 却打不开、`adb kill-server`+`start-server`
**已实测无效**、且当时机器上**只有 1 个 adb 进程**（故**不是** ledger 记的"多 adb 抢设备"）。
结论：本级联能覆盖 **"隧道断 / 注入器死"** 这一类；**不保证**覆盖"adb 整个看不见设备"这一类，
后者仍需人看一眼手机（重插线/解锁/确认 USB 调试）。**不把 #4 说成能修好一切。**

**明确不做**：不自动改 USB 模式、不自动动第三方工具（GameViewer 等）、不自动 `adb reconnect` 之外
的重置手段。
