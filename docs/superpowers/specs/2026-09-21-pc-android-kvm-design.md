# PC ↔ Android 键鼠共享 · 设计文档

- **日期**：2026-09-21
- **状态**：设计已确认，验证 0 已实测通过，待写实现计划
- **目标平台**：Windows 11 (x64) + 小米 HyperOS 3.0 / Android 16

---

## 1. 背景与目标

让 Windows PC 的键盘鼠标**无缝跨越**到 Android 设备上操作。鼠标推到显示器外侧边缘，控制权移交手机；在手机上把光标推回邻接边缘，控制权收回。

### 目标形态（硬性需求）

| 项 | 要求 |
|---|---|
| **画面** | **不传画面、不镜像、PC 上不开任何窗口**。用户直接看手机自己那块屏 |
| 方向 | PC 键鼠 → 手机 |
| 交互 | **边缘跨越**（不是热键切换，也不是手机端主动接管） |
| 传输 | 先 USB（adb）跑通，再考虑无线 |
| PC 侧足迹 | 绿色免安装单文件 exe；不写注册表、不装服务、不开机自启 |
| **手机侧足迹** | **零安装**——无 APK、无图标、无权限弹窗、无残留 |

> **关于"不传画面"的红线**：scrcpy 那种"在 PC 上开窗口镜像手机"**不是**本项目要做的形态。scrcpy 在本项目中仅作为一次性验证探针使用（见第 5 节），它提供的画面窗口与最终产品无关。

## 2. 为什么不用现成方案

调研结论（2026-09）：

| 项目 | 状态 | 为什么没采用 |
|---|---|---|
| **input-leaf** (Apache 2.0) | 44★，活跃 | 依赖 Deskflow 服务端；PC 侧要装服务；且光标是自绘浮层，盖不住系统面板 |
| **jglanz/deskflow-android** (MIT) | 131★，F-Droid 上架，**停更 14 个月** | 同上 |
| **Deskflow** 服务端 | 免费开源，winget 可装 | **被否决**，两个理由见下 |

**否决 Deskflow 的原因**（用户明确给出）：

1. **不想在办公机装东西** —— Deskflow 要装服务端 + 全局低级键盘钩子（`WH_KEYBOARD_LL`），而本机运行着网易青骓（`QzhddrGuard` / `QzhddrSrv`），键盘钩子的行为特征与键盘记录器一致，风险不对等。
2. **嫌那套难用** —— 配置繁、要拖屏幕网格、双项目拼接、掉线。

**已确认的硬冲突**：

> 「PC 键鼠控制手机」与「PC 上不装任何东西」在物理上不可兼得。

要让 PC 的键鼠事件跑到手机，PC 上**必须**有进程读取它们（钩子 / Raw Input / 内核驱动，三选一）。用户已选择：**保留方向，放松"零文件"约束**，接受一个绿色免安装 exe。

**本方案的核心卖点**：PC 侧足迹 = 一个可随时删除的单文件；**手机侧零安装**；**全程不用任何全局钩子**。

## 3. 运行环境（实测）

| 项 | 值 |
|---|---|
| 显示器 | 2 块，`DISPLAY2`(主, 0,0) + `DISPLAY1`(1920,0)，均 1920×1080 |
| 虚拟桌面 | 0,0 → 3840×1080 |
| DPI | 96（100% 缩放，无 DPI 缩放假象） |
| 网络 | 仅以太网 `10.222.38.129`，**本机无无线网卡** |
| adb | `D:\software\platform-tools\adb.exe` v37.0.1 |
| 终端安全 | 网易青骓（QzhddrGuard / QzhddrSrv / QzhddrUpdate / UserModePro）+ Windows Defender |
| 虚拟显示驱动 | `GameViewer Virtual Display Adapter`、`Sharing Monitor`（可能干扰"光标在哪块屏"的判断） |
| 手机 | 小米 `25053RP5CC`（codename `violin`），HyperOS 3.0（`OS3.0.304.0.WOTCNXM`）/ Android 16 (SDK 36)，**未 root** |
| 手机屏幕 | **2136 × 3200 @ 400dpi（竖屏）** |
| 手机 SELinux | Enforcing |
| shell 用户 | `uid=2000(shell)`，**属组含 `3011(uhid)`** |

**几何推论**：手机只能挂在最外侧——`DISPLAY2` 左边（x=0）或 `DISPLAY1` 右边（x=3840）。中间那条边被另一块屏占用。

**长宽比失配**：PC 侧边缘高 **1080**，手机竖屏高 **3200**，比例约 **1 : 2.96**。见第 7 节"两套比例，不能混用"。

## 4. 为什么必须用 UHID（而不是注入事件）

Android 有两条把输入送进去的路：

| | SDK 注入 `injectInputEvent` | **UHID**（写 `/dev/uhid`） |
|---|---|---|
| 光标 | ❌ **画不出**（Android 固有行为） | ✅ 系统绘制的真光标 |
| 盖住通知栏/快捷设置/锁屏 | ❌ 画不上去 | ✅ 原生覆盖 |
| 应用看到的 | 一串注入的事件 | **真实 HID 设备** |
| hover / 文本字段 I 型光标 / 右键菜单 | 语义缺失 | ✅ 原生正确 |
| 键盘 | 要另做一套 | ✅ 同一套机制顺便解决 |
| 需要的权限 | shell uid | shell uid（**一样**） |

**关键点：本项目必须有可见光标**（用户看的是手机自己的屏，没有光标就无从操作），所以 `injectInputEvent` 直接出局。

> 参考：scrcpy 文档与社区结论一致——"there is no way to show the mouse on the device when injecting mouse events via the InputManager"。scrcpy 3.3 专门加 UHID 鼠标模式正是为此。

## 5. 验证 0 的实测结论

用 `scrcpy --mouse=sdk` 与 `scrcpy --mouse=uhid` 作为一次性探针（免安装便携包，验完即删），在本机 + 目标手机上实测：

| 实测现象 | 结论 |
|---|---|
| scrcpy 连上，画面正常 | ✅ adb + USB 通路正常 |
| `--mouse=sdk`：**点击 App 有反应，但无光标** | ✅ `INJECT_EVENTS` 权限正常，**Android 16 未封锁 shell 注入**；❌ SDK 注入确认画不出光标 |
| `--mouse=uhid`：**光标出现且可移动** | ✅ `/dev/uhid` 可写；✅ 系统能绘制真光标；✅ **`app_process` 在 HyperOS 3.0 / Android 16 上可用** |

**最大的归零风险已排除**：原本担心 Android 16 收紧非 root 注入，实测未发生。

**第二个结论是意外收获**：scrcpy 靠 `app_process` 跑设备端进程且不装 APK——它在本机跑通，等于**验证了"手机侧零安装"这条路可行**。

**scrcpy 在此仅为探针，不是方案**，验完删除。

## 6. 架构

```
┌─ Windows（绿色单文件 exe，关掉即消失）───────────┐
│                                                   │
│  InputCapture   Raw Input (RIDEV_INPUTSINK)       │
│       │         不挂钩子，全局收事件（含非焦点时） │
│       ▼                                           │
│  EdgeTracker    光标位置 + 边缘判定 + 状态机       │
│       │         IDLE ⇄ TAKEOVER                   │
│       ├──────────────┐                            │
│       ▼              ▼                            │
│  Suppressor     Transport                         │
│  置顶小窗取焦点   │                               │
│  + ClipCursor    │                                │
│                  │                                │
│  TrayUi  托盘图标 +「手机在哪一侧」+ 灵敏度        │
└──────────────────┼────────────────────────────────┘
                   │ adb（USB 线 / 无线调试）
                   │ push + app_process 拉起
┌──────────────────┼────────────────────────────────┐
│ 手机侧：零安装（无 APK、无图标、无权限弹窗）        │
│                  ▼                                │
│  UhidInjector（常驻进程，跑在 shell uid）          │
│       │                                           │
│       ├─ 打开 /dev/uhid，写入组合 HID 报告描述符   │
│       │   （键盘 + 相对鼠标 + 滚轮）               │
│       └─ 循环：读 socket → 编码 HID 报告 → 写入    │
└───────────────────────────────────────────────────┘
```

### 三个关键设计决策

**① Android 侧零安装。** 不用 APK——`adb push` 一个 dex/jar 到 `/data/local/tmp`，用 `app_process` 拉起，用完即散。无图标、无权限弹窗、无残留。**此路径已由验证 0 实测确认可行。**

**② 传输层可替换。** 协议只定一次，底下挂 USB 和无线调试两个通道。先用 USB 把交互跑通，网络问题留到最后——把不确定性拆开，一次只验证一个变量。

**③ 抑制靠焦点不靠钩子。** 见第 9 节。

**Shizuku 已从设计中移除**：注入只需 shell uid，而 adb（无线调试同理）本身就能提供，多一层依赖没有收益。

## 7. 状态机、坐标与协议

### 状态机

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐  光标触外侧边缘且继续外推   ┌───────────┐
   │  IDLE   │ ─────────────────────────► │ TAKEOVER  │
   │ 正常用PC │                            │ 抑制已激活 │
   └─────────┘ ◄───────────────────────── └───────────┘
                    LEAVE + 恢复光标/焦点
```

- `IDLE → TAKEOVER` 判定必须是「贴边 **且** 仍在继续往外推」，不能只判"贴边"，否则光标停在边缘不动就会反复穿越。
- `TAKEOVER → IDLE` 之后要加**回程冷却**：光标必须离开边缘安全带才重新武装，否则回来的瞬间会被弹回去。这是同类软件最经典的 bug。

### 谁拥有光标位置

**PC 端持有虚拟光标模型**（坐标系 = 手机屏幕像素）。理由：边缘判定与 `ENTER` 逻辑聚在一处，保持一个状态机；手机侧保持"哑执行器"。

**隐藏前提**：进入 `TAKEOVER` 后 PC 光标被 `ClipCursor` 锁死，`GetCursorPos` 读出的是不动的值。所以此时只能用 Raw Input 的 `WM_INPUT` 提供的鼠标**相对增量**（`lLastX` / `lLastY`）推进虚拟光标。绝对坐标只在跨越那一瞬间用于计算入屏点。**这两套坐标不能混用。**

### 推角落归零（UHID 带来的新问题及解法）

UHID 鼠标是**相对位移**设备，没有"把光标放到 (x,y)"的能力。但边缘跨越需要精确设定入屏点。

**解法**：进入 `TAKEOVER` 时先发一串大幅向左上的相对位移（如 −10000, −10000），系统会把它钳制到 `(0,0)`；同时把虚拟光标也置为 `(0,0)`——**两边强制对齐**，再相对移动到目标入屏点。

代价是每次跨越多两次 USB 往返（几毫秒），换来光标位置永不漂移。

### 两套比例，不能混用

| 阶段 | 用什么 | 为什么 |
|---|---|---|
| **去程入屏点** | **比例映射** `phoneY = pcY / 1080 * 3200` | 保证 PC 边缘顶端 → 手机顶端、底端 → 底端 |
| **TAKEOVER 期间** | **1:1 相对增量**，不缩放 | 鼠标手感必须像鼠标；沿用 2.96 倍会快到不可用 |

**这是最易写错的地方**：全程用比例映射 → 鼠标快约 3 倍；全程用 1:1 → 入屏点错位。

**灵敏度留一个可调旋钮**，默认 1.0。注意 `lLastX` / `lLastY` 是 mickeys（原始计数）而非像素，Windows 指针加速不作用于它——1:1 只是起点，真实手感需现场标定。

### 协议

二进制、定长、小端。语义化——**HID 报告编码是手机侧的实现细节，不上协议**。

| 类型 | 载荷 | 方向 |
|---|---|---|
| `ENTER` | int16 x, int16 y（入屏点，手机屏坐标） | PC → 手机 |
| `MOVE` | int16 dx, int16 dy（**相对**，已按灵敏度换算并钳制） | PC → 手机 |
| `BUTTON` | uint8 btn(1左 2右 3中), uint8 down | PC → 手机 |
| `SCROLL` | int16 dx, int16 dy（滚轮格） | PC → 手机 |
| `KEY` | uint16 scancode, uint8 down, uint8 mods | PC → 手机 |
| `LEAVE` | 无 | PC → 手机 |
| `CONFIG` | uint8 edge, uint16 pcEdgeLen, uint16 phoneW, uint16 phoneH | 双向握手 |
| `PING` / `PONG` | uint32 seq | 双向，~1s |

**坐标钳制**：PC 端保证虚拟光标不越界——若 `vx + dx` 越界，就只发刚好推到边界的量（`dx' = 0 - vx` 或 `phoneW - 1 - vx`）。这样系统光标与虚拟光标接受相同增量、做相同钳制，永远同步。

**回程发起方**：`LEAVE` 由 **PC 端**发出（因为虚拟光标位置 PC 持有）。手机侧从不主动发 `LEAVE`。

### 键盘

Windows scancode → HID Usage ID（USB HID Usage Tables, Keyboard/Keypad page `0x07`）的映射表。修饰键是 HID 报告里的 modifier byte——比 `metaState` 更原生，输入法/快捷键全部正确。`HOME` / `BACK` / `APP_SWITCH` / 音量 / 媒体键走 Consumer Page (`0x0C`)。

## 8. 抑制机制（核心设计）

**控制权移交到手机时，弹一个获得焦点的置顶小窗。**

原理：Windows 把键盘输入发给**前台窗口**。只要窗口拿到前台，按键就进这个窗口，底下的应用收不到——**不需要任何全局钩子**。再配 `ClipCursor` 把鼠标锁进小区域，接管完成。收回时销毁窗口、`ClipCursor(NULL)`、把焦点还给原窗口（接管前先 `GetForegroundWindow` 存一下）。

**好处**：

- 零钩子、零驱动，青骓那边没有键盘记录器特征
- 小窗顺便就是 UX 指示器——"控制中 → 手机"直接显示在上面
- 没有钩子，就没有"装了不生效"和"被 EDR 拦掉"的不确定性

**已知限制（设计限制，非 bug）**：`Win` 键和 `Ctrl+Alt+Del` 这类系统级热键仍会被操作系统截走。办公场景可接受。

## 9. 三个必须处理的边界情况

**一等公民，不是"以后再说"。** 断线那条决定这套东西是"偶尔抽风"还是"能日常用"。

### ① 断线必须立刻解除抑制

若手机在 `TAKEOVER` 中掉线，PC 鼠标被锁死、键盘全进了一个看不见的窗口——**用户被锁在自己的电脑外面**。

- 心跳超时（~2s 无 `PONG`）→ 强制回 `IDLE`
- 兜底：进程崩掉时 `ClipCursor` 由系统自动释放，exe 被杀也能救回。**这是兜底，不能只靠它**

**附带的好处**：adb 断线 → 手机侧 `app_process` 进程退出 → `/dev/uhid` 的 fd 关闭 → 内核销毁虚拟设备 → Android 认为鼠标被拔出 → 光标自动消失。**手机侧天然自清理，不需要显式清理逻辑。**

### ② 前台被抢走就漏键

抑制依赖"我的窗口在前台"。UAC 弹窗（安全桌面）、锁屏、别的程序抢焦点都会让按键漏到别处。

- 监听前台窗口变化，一旦不是我们 → **立刻强制退出 `TAKEOVER`**

### ③ 紧急逃逸键

`Ctrl+Alt+Esc` 之类，无论什么状态都强制回 `IDLE`。有了 ② 它其实是冗余的，但这类软件里冗余的手动逃生口很值。

## 10. 验证顺序

**原则**：按"能杀死方案的程度"排序，一次只引入一个变量。

| # | 验什么 | 状态 |
|---|---|---|
| **0** | Android 16 能否非 root 拿到真光标 | ✅ **已通过**（见第 5 节） |
| **1** | 焦点小窗真能吃掉键盘 | ⬜ 待验，~10 分钟 |
| **2** | Raw Input 拿相对增量 + 非焦点收键 | ⬜ 待验，~30 分钟 |
| **3** | adb 通路 | ✅ 已通过（验证 0 顺带验了） |
| **4** | **手机侧零安装跑通**：push dex + `app_process` + 自建 HID 描述符 | ⬜ 待验（scrcpy 间接证明可行，需自建复现） |

### 失败时的岔路

- **验证 1 挂了** → 焦点抑制不成立，必须上 `WH_KEYBOARD_LL`（回到青骓风险）或内核驱动。**这是真正的决策点**，需重开一轮权衡。
- **验证 4 挂了** → 回退到装 APK（仍用 UHID 注入），牺牲"手机零安装"但保住光标。

### 已知前置条件

小米 HyperOS 需要开启**「USB 调试（安全设置）」**才允许 shell 注入。当前设备实测已可用。

## 12. 未决事项

- 无线阶段可行性取决于办公网是否允许 PC(有线) ↔ 手机(Wi-Fi) 直连。USB 阶段不受影响。

- 组合 HID 报告描述符（键盘 + 相对鼠标 + 滚轮）需要自建，可参考 scrcpy 的 UHID 实现与标准 HID Usage Tables。
