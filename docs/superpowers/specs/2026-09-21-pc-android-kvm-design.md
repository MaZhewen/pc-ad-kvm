# PC ↔ Android 键鼠共享 · 设计文档

- **日期**：2026-09-21
- **状态**：设计已确认（第 1–3 节），待验证 0 结果后进入实现计划
- **目标平台**：Windows 11 (x64) + Android 16

---

## 1. 背景与目标

让 Windows PC 的键盘鼠标能够**无缝跨越**到 Android 设备上操作，即 Synergy / Deskflow 那种软件 KVM 体验：鼠标推到显示器外侧边缘，控制权移交手机；在手机上把光标推回邻接边缘，控制权收回。

**明确的目标形态**（来自需求澄清）：

- 方向：**PC 键鼠 → 手机**
- 交互：**边缘跨越**（不是热键切换，也不是手机端主动接管）
- 传输：**先 USB（`adb reverse`）跑通，再考虑无线**
- PC 侧足迹：**绿色免安装单文件 exe**，不写注册表、不装服务、不开机自启，关掉进程机器上零残留
- 不传画面（Synergy 语义——手机那块屏自己显示内容，PC 不镜像）

---

## 2. 为什么不用现成方案

调研结论（2026-09）：

| 项目 | 状态 | 为什么没采用 |
|---|---|---|
| **input-leaf** (Apache 2.0) | 44★，活跃（2026-09-18 提交） | 依赖 Deskflow 服务端；PC 侧要装服务 |
| **jglanz/deskflow-android** (MIT) | 131★，F-Droid 上架，**停更 14 个月** | 同上 |
| **Deskflow** 服务端 | 免费开源，winget 可装 | **被否决的两个理由** |

**否决 Deskflow 的原因**（用户明确给出）：

1. **不想在办公机装东西** —— Deskflow 要装服务端 + 全局低级键盘钩子（`WH_KEYBOARD_LL`），而本机运行着网易青骓（`QzhddrGuard` / `QzhddrSrv`），键盘钩子的行为特征与键盘记录器一致，风险不对等。
2. **嫌那套难用** —— 配置繁、要拖屏幕网格、双项目拼接、掉线。

**已确认的硬冲突**：

> 「PC 键鼠控制手机」与「PC 上不装任何东西」在物理上不可兼得。

要让 PC 的键鼠事件跑到手机，PC 上**必须**有进程读取它们（钩子 / Raw Input / 内核驱动，三选一）。蓝牙、USB、网络只解决"怎么送过去"，不解决"怎么拿到"。用户已明确选择：**保留方向，放松"零文件"约束**，接受一个绿色免安装 exe。

**因此本方案的核心卖点是**：PC 侧足迹降到"一个可随时删除的单文件"，且**不用任何全局钩子**。

## 3. 运行环境（实测）

| 项 | 值 |
|---|---|
| 显示器 | 2 块，`DISPLAY2`(主, 0,0) + `DISPLAY1`(1920,0)，均 1920×1080 |
| 虚拟桌面 | 0,0 → 3840×1080 |
| DPI | 96（100% 缩放，无 DPI 缩放假象） |
| 网络 | 仅以太网 `10.222.38.129`，**本机无无线网卡** |
| adb | `D:\software\platform-tools\adb.exe` v37.0.1 |
| 终端安全 | 网易青骓（QzhddrGuard / QzhddrSrv / QzhddrUpdate / UserModePro）+ Windows Defender |
| 虚拟显示驱动 | `GameViewer Virtual Display Adapter`、`Sharing Monitor`（可能干扰"光标在哪块屏"的判断） |
| 手机 | 小米 `25053RP5CC`（codename `violin`），HyperOS 3.0（`OS3.0.304.0.WOTCNXM`）/ Android 16 (SDK 36) |
| 手机屏幕 | **2136 × 3200 @ 400dpi（竖屏）** —— 见下方"长宽比失配" |

**长宽比失配（实测发现的设计问题）**：PC 侧边缘高度只有 **1080**，手机竖屏高度是 **3200**，比例约 **1 : 2.96**。这意味着去程的比例映射会把 PC 边缘的 1080 px 拉满整个 3200 px 的手机屏——**入屏定位是对的，但如果 TAKEOVER 期间也沿用这个比例，鼠标会快约 3 倍，完全不可用**。解决方案见第 6 节"两套比例，不能混用"。

**手机厂商前置条件（已确认适用）**：小米 HyperOS 需要开启**「USB 调试（安全设置）」**才允许 shell 注入。当前设备预检未报权限错，但该预检是弱信号（`KEYCODE_UNKNOWN` 可能在权限检查前被短路），真正的判定以验证 0 为准。

**几何推论**：手机只能挂在最外侧——`DISPLAY2` 左边（x=0）或 `DISPLAY1` 右边（x=3840）。中间那条边被另一块屏占用。

## 4. 架构

```
┌─ Windows (绿色单文件 exe，关掉即消失) ────────────┐
│                                                   │
│  InputCapture   Raw Input (RIDEV_INPUTSINK)       │
│       │         不挂钩子，全局收事件（含非焦点时） │
│       ▼                                           │
│  EdgeTracker    光标位置 + 边缘判定 + 状态机       │
│       │         IDLE ⇄ TAKEOVER                   │
│       ├──────────────┐                            │
│       ▼              ▼                            │
│  Suppressor     Transport (TCP)                   │
│  置顶小窗取焦点   │                               │
│  + ClipCursor    │                                │
│                  │                                │
│  TrayUi  托盘图标 +「手机在哪一侧」+ 端口          │
└──────────────────┼────────────────────────────────┘
                   │  USB: adb reverse tcp:P tcp:P
                   │  或  Wi-Fi: 直连
┌──────────────────┼────────────────────────────────┐
│  Android App (Kotlin)                             │
│                  ▼                                │
│  Transport (TCP client)                           │
│       │                                           │
│       ▼                                           │
│  Injector  ← 接口，两个实现：                      │
│       A. adb shell uid → IInputManager            │
│          .injectInputEvent   (真光标，不用装东西)  │
│       B. Shizuku            (无线时用)             │
│       │                                           │
│       ▼                                           │
│  ConfigUi  服务器地址/端口 + 连接状态              │
└───────────────────────────────────────────────────┘
```

### 三个关键设计决策

**① 传输层可替换。** 协议只定一次，底下挂两个通道：USB（`adb reverse`，现在就能通，不碰办公网）和 Wi-Fi（要啃网络策略）。先用 USB 把注入和交互跑通，网络问题留到最后——把不确定性拆开，一次只验证一个变量。

**② 注入层可替换。** `Injector` 是接口，先实现 adb 那条（`adb reverse` 已经连上手机，直接跑 shell uid 注入器，**不用装 Shizuku**），无线阶段再补 Shizuku 实现。Android 侧越薄，换注入实现越无痛。

**③ 抑制靠焦点不靠钩子。** 见第 7 节。

## 5. 状态机

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐  光标触外侧边缘且继续外推   ┌───────────┐
   │  IDLE   │ ─────────────────────────► │ TAKEOVER  │
   │ 正常用PC │                            │ 抑制已激活 │
   └─────────┘ ◄───────────────────────── └───────────┘
                    LEAVE + 恢复光标/焦点
```

**`IDLE → TAKEOVER` 判定必须是「贴边 **且** 仍在继续往外推」**，不能只判"贴边"——否则光标停在边缘不动就会反复穿越。

**`TAKEOVER → IDLE` 之后要加回程冷却**：光标必须离开边缘安全带才重新武装，否则回来的瞬间会被弹回去。这是同类软件最经典的 bug。

## 6. 坐标与协议

### 谁拥有手机上的光标位置

**PC 端持有，发绝对坐标。** 理由：边缘判定逻辑与 `ENTER` 逻辑聚在一处，保持**一个状态机**；Android 侧退化成"哑注入器"，将来换注入实现代价最小。

**隐藏前提（必须遵守）**：进入 `TAKEOVER` 后 PC 光标被 `ClipCursor` 锁死，`GetCursorPos` 读出的是**不动的**值。所以此时只能用 Raw Input 的 `WM_INPUT` 提供的鼠标**相对增量**（`lLastX` / `lLastY`）推进虚拟光标。绝对坐标只在跨越那一瞬间用一次。**这两套坐标不能混用。**

### 协议

二进制、定长、小端。够用即可，不做扩展性设计。

| 类型 | 载荷 | 方向 |
|---|---|---|
| `ENTER` | int16 x, int16 y（手机屏绝对坐标，入屏点） | PC → A |
| `MOVE` | int16 x, int16 y（绝对） | PC → A |
| `BUTTON` | uint8 btn(1左 2右 3中), uint8 down | PC → A |
| `SCROLL` | int16 dx, int16 dy（滚轮格） | PC → A |
| `KEY` | uint16 scancode, uint8 down, uint8 mods | PC → A |
| `LEAVE` | 无 | PC → A |
| `CONFIG` | uint8 edge, uint16 pcEdgeLen, uint16 phoneW, uint16 phoneH | 双向握手 |
| `PING` / `PONG` | uint32 seq | 双向，~1s |

### 坐标映射（比例映射）

手机挂 `DISPLAY1` 右侧（PC 右边缘 x=3840）：

- **去程**：`phoneY = pcY / 1080 * phoneH`，`phoneX = 0`（从手机左边入屏）
- **回程**：**PC 端**检测到虚拟光标撞到 `x <= 0`（手机的邻接边缘）→ PC 退出 `TAKEOVER` 并发出 `LEAVE` 通知 Android 停止等待输入 → `pcY = phoneY / phoneH * 1080`，`pcX = 3839`（贴右边缘内侧）

> **注意发起方**：因为虚拟光标位置由 PC 持有（见上），回程判定也在 PC 端完成。Android 从不主动发 `LEAVE`——它只被动接收并停止注入。协议表里 `LEAVE` 标为 `PC → A` 与此一致。

### 两套比例，不能混用（实测数据暴露的问题）

| 阶段 | 用什么 | 为什么 |
|---|---|---|
| **去程入屏点** | **比例映射** `phoneY = pcY / 1080 * 3200` | 保证 PC 边缘顶端 → 手机顶端、底端 → 底端。"从边上某处跨进去"这个直觉只有比例映射能给 |
| **TAKEOVER 期间** | **1:1 相对增量**，不缩放 | 鼠标手感必须像鼠标。沿用 2.96 倍的话鼠标会快到不可用 |

**这是本节最容易写错的地方**：

- 全程用比例映射 → 鼠标在手机上快约 3 倍
- 全程用 1:1 → 入屏点错位（PC 光标在边缘中点，手机光标出现在屏幕 1/3 处）

**灵敏度留一个可调旋钮**，默认 1.0，实测时手调。注意 Raw Input 的 `lLastX` / `lLastY` 是 mickeys（原始计数）而非像素，Windows 的指针加速不作用于它——所以 1:1 只是起点，真实手感必须现场标定。

**配置项只有两个**：手机挂在哪个显示器的哪一侧。没有屏幕网格，没有拖拽。

### 键盘

Raw Input 同样能拿到键盘。工作量集中在**一张 Windows scancode → Android `KEYCODE_*` 的映射表**（纯体力活，几十行）。修饰键（Ctrl/Alt/Shift/Meta）转成 `metaState`。`HOME` / `BACK` / `APP_SWITCH` / 音量 / 媒体键单独走特殊规则。

## 7. 三个必须处理的边界情况

这三个是**一等公民**，不是"以后再说"。断线那条尤其——它决定这套东西是"偶尔抽风"还是"能日常用"。

### ① 断线必须立刻解除抑制

若手机在 `TAKEOVER` 中掉线，PC 鼠标被锁死、键盘全进了一个看不见的窗口——**用户被锁在自己的电脑外面**。

- 心跳超时（~2s 无 `PONG`）→ 强制回 `IDLE`
- 兜底：进程整个崩掉时 `ClipCursor` 由系统自动释放，所以 exe 被杀也能救回来。**这个是兜底，不能只靠它。**

### ② 前台被抢走就漏键

抑制完全依赖"我的窗口在前台"。UAC 弹窗（安全桌面）、锁屏、别的程序抢焦点，都会让按键漏到别处。

- 监听前台窗口变化，一旦不是我们 → **立刻强制退出 `TAKEOVER`**

### ③ 紧急逃逸键

`Ctrl+Alt+Esc` 之类，无论什么状态都强制回 `IDLE`。有了 ② 它其实是冗余的，但这类软件里冗余的手动逃生口很值。

## 8. 抑制机制（核心设计）

**控制权移交到手机时，弹一个获得焦点的置顶小窗。**

原理：Windows 把键盘输入发给**前台窗口**。所以只要窗口拿到前台，按键就进这个窗口，底下的应用收不到——**不需要任何全局钩子**。再配 `ClipCursor` 把鼠标锁进小区域，接管完成。收回时销毁窗口、`ClipCursor(NULL)`、把焦点还给原窗口（接管前先 `GetForegroundWindow` 存一下）。

**好处**：

- 零钩子、零驱动，青骓那边没有键盘记录器特征
- 小窗顺便就是 UX 指示器——"控制中 → 手机"直接显示在上面，用户永远知道控制权在哪
- 没有钩子，就没有"装了不生效"和"被 EDR 拦掉"的不确定性

**已知限制（设计限制，非 bug）**：`Win` 键和 `Ctrl+Alt+Del` 这类系统级热键仍会被操作系统截走。办公场景下可接受。

## 9. 验证顺序

**原则**：按"能杀死方案的程度"排序，不按实现顺序排。先验一旦失败整套东西就没意义的；能靠便宜手段验的绝不动代码。**一次只引入一个变量。**

| # | 验什么 | 怎么验 | 失败长什么样 | 成本 |
|---|---|---|---|---|
| **0** | Android 16 上行不行非 root 注入真鼠标光标 | **用 scrcpy 当探针，零代码** | 手机上不出光标 / 报权限错 | ~5 分钟 |
| **1** | 焦点小窗真能吃掉键盘 | 置顶小窗抢焦点后往记事本打字 | 字符仍进记事本 → 抑制不成立 | ~10 分钟 |
| **2** | Raw Input 拿相对增量 + 非焦点收键 | 50 行 C# 探针打印 `WM_INPUT` 数据和 `GetCursorPos` | 拿不到 `lLastX`/`lLastY` | ~30 分钟 |
| **3** | `adb reverse` 隧道 | `adb reverse` + 手机连 `127.0.0.1` 回显 | 隧道不通 | ~10 分钟 |
| **4** | 端到端最小闭环 | 前面全过才做 | — | 大头 |

### 验证 0 的取巧

scrcpy 的 `--mouse=sdk` 模式（**且是默认模式**）走的就是本方案计划用的那条路——在 Android API 层做输入注入，产生**真实系统光标**（相对的是 `uhid` / `aoa`，它们模拟物理 HID 设备，不是我们的路径）。

所以在目标手机 + Android 16 上跑一次 scrcpy，鼠标移到设备上能看见光标，就等于证明：

- shell uid 确实有 `INJECT_EVENTS` 权限
- Android 16 没有收紧这条路
- 真光标渲染正常

**顺带把验证 3 也验了**（scrcpy 本来就走 adb + USB）。一次操作，两个高风险项。

**scrcpy 在此是一次性探针，不是方案。** 免安装绿色压缩包，解压跑一次、验完删掉，不进系统、不留服务、不挂钩子。这与"把 Deskflow 装成长期服务端"是两回事。

### 失败时的岔路（提前定好）

- **验证 0 挂了** → Android 16 封了 shell 注入。退路：Shizuku（体验相同但要装东西 + 重启重激活）、无障碍（能跑但没真光标、没热键）、或方案归零。**这是唯一的归零风险点，所以排第一。**
- **验证 1 挂了** → 焦点抑制不成立，必须上 `WH_KEYBOARD_LL`（回到青骓风险）或内核驱动。**这是真正的决策点**，需重开一轮权衡，不是随手改代码。

### 已知前置条件

部分国产 ROM（小米/OPPO/vivo 等）需要额外开启**「USB 调试（安全设置）」**才能允许 shell 注入，否则注入会被静默拒绝。若验证 0 出现"连上了但没光标"，先查这一项。

## 11. 未决事项

- 无线阶段是否可行，取决于办公网是否允许 PC(有线) ↔ 手机(Wi-Fi) 直连。USB 阶段不受影响。
- 本机两个虚拟显示驱动（`GameViewer`、`Sharing Monitor`）是否干扰光标所在屏幕的判定，待验证 2 时观察。
- Android 侧注入键事件进入文本框的实际表现（软键盘类 App 可能不接收硬件键事件），待端到端阶段观察。
